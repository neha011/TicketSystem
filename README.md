# Support Ticket Management — `ticket-service`

Spring Boot 3.3 / Java 21 backend for the Support Ticket Management System. It exposes a REST
API under `/api/v1` for creating, listing, searching, updating, and commenting on support
tickets, and it is the single authority on what a valid ticket is:

- All length, enum, and required-field rules are enforced server-side, independently of any
  frontend validation. Validation is atomic — no record is modified unless every field in the
  request passes.
- Ticket status changes follow a strict state machine (`OPEN → IN_PROGRESS → RESOLVED → CLOSED`,
  with `CANCELLED` reachable from `OPEN` and `IN_PROGRESS`). `CLOSED` and `CANCELLED` are
  terminal. Illegal transitions are rejected with `409 Conflict`; undefined status values are
  rejected with `400 Bad Request`.
- Ticket and comment data is persisted to a relational database (PostgreSQL outside local
  development, H2 for local runs and tests) and survives application restarts.
- Concurrent updates are guarded by optimistic locking; callers echo back the ticket `version`
  they read and receive `409 Conflict` if it is stale.

API documentation is generated by springdoc-openapi and served in non-production profiles at
`/swagger-ui.html` (raw document at `/v3/api-docs`).

## Requirements

- JDK 21
- Maven 3.8+
- Docker (only for integration tests that use Testcontainers)
- PostgreSQL (only for non-local profiles; local development uses in-memory H2)

## Running locally

The `local` profile runs against in-memory H2 and needs no external database or credentials:

```bash
mvn spring-boot:run -Dspring-boot.run.profiles=local
```

The service listens on `http://localhost:8080`. Data in the `local` profile is in-memory and is
discarded when the process stops.

Against a real PostgreSQL instance:

```bash
export DB_URL=jdbc:postgresql://localhost:5432/tickets
export DB_USERNAME=tickets
export DB_PASSWORD=<password>
mvn spring-boot:run -Dspring-boot.run.profiles=prod
```

Outside `local`, the schema is managed exclusively by Flyway migrations in
`src/main/resources/db/migration`. Automatic schema generation is not used, and a failed
migration aborts startup before the service accepts any request.

## Building

```bash
mvn clean install          # compile, run tests, package
mvn clean package -DskipTests
```

## Running tests

```bash
mvn test                                  # everything
mvn test -Dtest=TicketServiceTest         # a single class
mvn test -Dtest='*PropertyTest'           # jqwik property-based tests only
```

Test layers in this project:

- Unit tests (`*Test`) — collaborators mocked, no Spring context.
- Property-based tests (`*PropertyTest`) — jqwik, covering invariants such as the status
  transition table, trimmed-length validation, and pagination.
- Slice tests — `@WebMvcTest` for controllers, `@DataJpaTest` for repositories.
- Integration tests — `@SpringBootTest` with Testcontainers PostgreSQL, so Docker must be
  running for those to pass.

## Environment variables

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `SPRING_PROFILES_ACTIVE` | no | `local` | Active profile: `local`, `test`, `staging`, or `prod`. Determines the database and schema strategy. |
| `DB_URL` | yes, outside `local` | — | JDBC URL of the PostgreSQL database, e.g. `jdbc:postgresql://host:5432/tickets`. |
| `DB_USERNAME` | yes, outside `local` | — | Database username. |
| `DB_PASSWORD` | yes, outside `local` | — | Database password. Supply via the environment or a secrets manager; never commit it. |
| `SERVER_PORT` | no | `8080` | HTTP port the service binds to. |
| `TICKET_KNOWN_USERS` | no | `alice,bob,carol` under `local`, empty elsewhere | Comma-separated identifiers accepted as a ticket assignee. Anything else is rejected with 422, so an empty value refuses every assignment. |

No secrets are stored in `application.yml`; configuration references these variables through
`${...}` placeholders.

## Project layout

```
src/main/java/com/ticketsystem/ticket
├── TicketServiceApplication.java
├── controller     HTTP boundary + centralized exception handling
├── service        business rules, including the pure status transition validator
├── repository     Spring Data JPA repositories and query specifications
├── domain         JPA entities, status/priority enums, transition table
├── dto            request/response payloads and mappers
├── validation     custom constraints (trimmed-length)
├── config         OpenAPI, security, Jackson, typed properties
└── exception      domain exception hierarchy mapped to HTTP statuses
```

Feature specs (requirements, design, task plan) live in `.kiro/specs/`; engineering conventions
live in `.kiro/steering/`.
